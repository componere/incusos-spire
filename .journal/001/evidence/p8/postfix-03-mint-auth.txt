--- what the log proves ---
Every 401 line carries instance_uuid:"" — the request was refused before the body
was decoded, so the service never learned which instance was being asked for and
therefore could not have resolved it. The one authenticated request for the same
nonexistent UUID carries instance_uuid:"00000000-0000-4000-8000-000000000000" and
reason "attestor: instance not found", which is the read-only credential actually
reaching the Incus API and coming back empty. Same body, same endpoint, same
second: the only difference is the token, and the only request that touched Incus
is the one that presented it.

The 401 for a missing header and the 401 for a wrong token are byte-identical:
both bodies hash to 3341bff062d83e3afeb943f83bbb079f5b45cc050e796ec282dde50b5906cb31
("{"error":"unauthorized"}"), both carry WWW-Authenticate: Bearer
realm="incus-spiffe-broker", and the log distinguishes them by neither: it records
the peer address and never the presented value. A caller cannot tell "you sent no
token" from "you sent the wrong one".
