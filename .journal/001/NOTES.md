## 2026-08-16 16:52 — P5 and P6 executed in parallel; both verified independently

**P5 — authorization: one hard negative result.** Incus 7.3 has **no** fine-grained auth API at all: `incus auth` is an unknown command and `/1.0/auth*` 404s; it is an LXD feature Incus did not adopt. Project-restricted TLS certs alone are far too coarse — both identities came out identical across 34 cases with full project-operator rights (create, delete, any config write incl. `security.privileged`, file pull, `/1.0/resources`). The Starlark **authorization scriptlet** is the only in-tree mechanism that works, and it achieved the exact grant for `spike-attestor-ro` (read-only, project-confined, every write/create/delete/exec/file/cross-project/host-resource call denied). It **cannot** express the writer's grant: `authorize(details, object, entitlement)` never receives the request body, so "set `user.spiffe-bootstrap`" and "set `volatile.uuid`" are indistinguishable. Smallest achievable writer grant is `instance:spike-spiffe/* can_edit`, which unavoidably also permits writing **any** config key including `volatile.uuid` (identity-anchor forgery), plus **delete** and **rename** — there is no separate delete entitlement, DELETE authorizes as `can_edit`.
I re-verified the security-critical claims first-hand rather than trusting the report: as `spike-attestor-ro`, reads of its own project succeed while `user.*` write, `volatile.uuid` PATCH, create, delete and `/1.0/resources` all return `Permission denied` (cross-project reads return an empty list rather than an error — filtered, not denied). As `spike-bootstrap-writer`, instance reads are denied but a raw PATCH of `user.spiffe-bootstrap` succeeds; on a throwaway instance I confirmed the writer can also PATCH `volatile.uuid` and DELETE the instance outright. Two further live findings worth carrying: upstream authorization docs are **stale** for 7.3 (`details.Username` does not exist; the real shape is `details.RequestDetails.{Username,Protocol,ProjectName,IsAllProjectsRequest}` plus `details.Certificate`), and routing `tls-restricted` away from the `tls` driver makes Incus **stop enforcing the certificate's project list**, so the scriptlet must re-implement confinement itself. The scriptlet is server-global and is deliberately left enabled; admin (unrestricted TLS) and unix access are unaffected and were re-verified after every change.

**P6 — UUID semantics: anchor confirmed, uniqueness is not.** Both a container pass and a real `images:debian/13` VM pass, no divergence in UUID behaviour. `volatile.uuid` is stable across stop/start, snapshot restore, and rename; it regenerates on copy/clone (including clone-from-snapshot) and on delete+recreate-same-name. Snapshot **restore keeps `volatile.uuid` but replaces `volatile.uuid.generation` with a fresh random value** — confirmed twice from the same snapshot, yielding two different generations, neither equal to the value stored in the snapshot. So rollback-sensitive generation semantics are **confirmed by experiment**, which is exactly what the guest-binding design needs. Live read-only check: `spire-server`'s `volatile.uuid` is still `089b0067-0c97-443e-8f42-c19776761f28`, identical to the P2 capture across three host reboots. `volatile.cloud-init.instance-id` was rejected as a fallback anchor because it changes on both copy and rename.
The prominent qualification: **uniqueness is not server-enforced.** A duplicate `volatile.uuid` set via `incus config set` was accepted and the UUID filter then returned two instances; `volatile.uuid.generation` is writable to an arbitrary value; format is validated but not uniqueness; tampering even propagates into VM guest DMI `product_uuid`. Combined with P5's writer residual this is one coherent risk: the anchor is correct, but it is only as trustworthy as the set of principals holding project config-write, and the attestor must fail closed on multi-match. That is now an explicit P7/P8 architecture question, not an authorization one.
Schema frozen in `evidence/p6/REFERENCE_SCHEMA.md`: all four draft fields kept (`instance_uuid` as sole required anchor; `project`, `generation_uuid`, `server` optional and equality-checked, never used for routing) and all six draft selectors kept, with `incus:status`, `incus:location`, `incus:cloudinit-id`, `incus:created-at` and guest DMI UUID rejected against cited observations. A UUID resolves in one authenticated call: `GET /1.0/instances?recursion=1&project=<p>&filter=config.volatile.uuid eq <uuid>`. Plugin boundary defined per AGENTS.md hexagonal rules — pure `internal/attestor` core with a consumer-owned `InstanceReader` port, `internal/incus/identity` read adapter, `cmd/incus-attestor` SPIRE adapter, `internal/incus/bootstrap` kept separate by credential.
