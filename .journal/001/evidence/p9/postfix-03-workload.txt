The two callers received DIFFERENT SPIFFE IDs from the SAME socket, because the agent
attested each caller's uid independently: unix:uid:0 -> /guest/demo, unix:uid:989 ->
/guest/demo-app. That is the Workload API doing real caller attestation inside the guest,
not a shared credential handed to whoever connects.

/tmp/spire-agent/public/api.sock srwxrwxrwx root:root

PRECISION NOTE: guest-agent-bootstrap.sh creates any MISSING directory component mode 0755.
Here /tmp/spire-agent and /tmp/spire-agent/public already existed from the previous run at
mode 0700, so the harness did not recreate them -- it added o+x to each, giving 0701. It
logged both actions:
    agent: /tmp/spire-agent was mode 700 and not traversable; added o+x for the non-root workload path
    agent: /tmp/spire-agent/public was mode 700 and not traversable; added o+x for the non-root workload path
0701 is the tighter of the two outcomes and is sufficient: traversal needs only x. SPIRE
itself serves the socket 0777 (srwxrwxrwx above), so the directory was the only barrier.
